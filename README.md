# Listings

A personal page that pulls sale items and wishlist prices from many shops.

- `wishlist.txt`  one URL per line: product pages to follow and price-track.
- `stores.json`   one entry per store. `platform` is `shopify` (open feed), `page` (read price from the product page) or `link` (just a link card). `browse: true` scans the whole store for sale items. `currency` is only a fallback for Shopify stores: they localise prices by visitor country, so the build asks each one which currency it is quoting. `group` is the store's category; items from `clothing` stores, and from stores marked `"mixed": true`, are sorted one by one into tops, bottoms, dresses, skate gear and so on (rules in `build.py`), with `kind` as the fallback for items no rule matches. Clothing also gets a type within its kind where the listing says (jeans among bottoms, boots among footwear: `TYPES` in `build.py`). `"all": true` lists a store's whole in-stock range, not only its discounts (shown under Everything). `"fits": "women"` or `"men"` marks a boutique whose unlabelled items are all one or the other. `feed` names another host to read a store's Shopify data from, for a shop whose own address is a custom front end (`"host": "skims.com", "feed": "skimsbody.myshopify.com"`); items keep the shop's address. `brand` overrides the brand name for a brand's own store when its feed leaves it blank, puts something else there or spells it several ways. `"collections": ["visvim", "asics"]` reads only those Shopify collections, for a big retailer that rate-limits a full catalog read, or a sneaker shop where only a few brands are worth tracking; `"all": ["visvim"]` then lists the full in-stock range of just those collections.
- **Stores that are not open Shopify feeds** are read from their own listing pages or shop API by `listings.py`, then go through the same tracking, sorting and listing as Shopify products. A `page` store with `browse: true` names how in `read`: `"woocommerce"` (the WooCommerce Store API), `"netsuite"` (a NetSuite shop's `/api/items`, with `feed` for the shop's host) or `"listing"`: the category pages in `pages` (an address, or `[address, "mens jeans"]` to say what the page lists, which sorts items that name no type), read `via` their JSON-LD (`"ld"`), the product data the page embeds for its scripts (`"json"`), the grid's `data-pid` tiles (`"tiles"`) or links to product pages matching `link` with the prices after them (`"links"`). `paging` adds a page to the address (`"?start={start}&sz=48"` with `"size": 48`, `"?page={n}"`, or `"next"` to follow the page's own next link); a listing stops at the first page with nothing new. `sold` is the shop's own sold-out mark in a tile (grids that print a hidden "sold out" in every tile get no default), `was_class`, `name_class` and `brand_class` its classes for the original price, the name and the brand where the usual guesses miss (`"name_alt": true` takes the name from the photo's alt text), `product_path` and `product_url` (`"/us/en/product/{id}"`) make an address for embedded products that carry only a handle or an id, `skip` a pattern of items to leave out (Leffot's preorders are priced at their deposit), `"whole": true` says the pages cover the store's whole range, `max_pages` caps one store, `delay_seconds` slows one store to the `Crawl-delay` its robots.txt asks for (Visvim: 20 s). Three more settings cover tiles that keep their facts somewhere other than in the words they print: `tile_json` names an attribute that holds the product's own data as JSON (`"product-info"` for Lilly Pulitzer's `data-product-info="{...}"`, which carries the name, both prices and the sizes); `"tile_ids": true` prices a grid that prints no price at all from the list the page hands its analytics, matched to each tile by its product id (Johnny Was), and `"link_ids": true` does the same for a grid with no tiles to mark, matching the part of each product's address that spells its name or its id (Kendra Scott); `size_class` names the element for one size swatch where the usual `data-size` attributes are not there, and `"size_stock": true` says a tile lists every size the shop has, so a tile with none left is sold out. Every address is checked against the host's robots.txt first, wildcards included, and skipped if disallowed. Listing pages are 1 to 4 MB, so only these requests ask for gzip. Talbots is read with a deliberately small page and a low cap (`sz=18`, `max_pages: 6`): its clearance listing reads cleanly that way, but its bot check turns an address away for a long while once it is asked for a bigger page.
- **What a listing gives up besides the price.** Sizes are read where the page carries them — a list of sizes in the store's own product data, the variants of a JSON-LD Product, or the size swatches of a tile — and the sold-out ones are left out, so an item says what is still in stock. The same goes for the original price (a struck-through price, a `listPrice` or `compare-at` field, a `data-product-listprice` attribute), the in-stock state (a tile's `data-product-availability`, a `stockState`, an `isSoldOut`) and the currency the page names for its prices. Many listings still carry none of it: a markdown then shows when tracking sees the price fall ("↓ tracked"), and a page that names no currency falls back to the store's `currency`.
- `build.py`      fetches everything and writes `docs/data.json`; `listings.py` reads the stores above. Standard library only.
- `history.py`    what is remembered about every product (`data/state/`, one file per store) and the numbers worked out from it (`docs/metrics.json`). `py history.py` recomputes the metrics from the files on disk.
- `docs/`         the page GitHub Pages serves. `docs/chat.js` is the shopping assistant; `docs/vendor/` holds the official Anthropic SDK bundled into one file (see the note there).
- `.claude/agents/feed-scout.md`  the brief for a Claude Code agent that looks for an openly served product feed for stores the build cannot read yet (`link` and `page` stores, or stores not listed). It only reports endpoints that answer plain requests; a store that refuses automated reading stays a link.
- `.github/workflows/update.yml`  publishes the site with GitHub Pages (source: GitHub Actions). **Each run starts the next**: 20 minutes after it began, a run asks for a "cycle" run, which refreshes the 95 stores read longest ago (`build.py --stalest 95`; the others keep their items), so every store comes round about once an hour. GitHub's own timers start runs late or not at all (most hourly ones never ran), so they are kept only as a way back in if the chain breaks. The daily timer and the "Run workflow" button refresh every store. A push that changes `build.py`, `history.py`, `listings.py` or `stores.json` runs a cycle (stores never read before come first), not a refresh of everything: several pushes in an hour once re-read every store each time, and the stores answered with refusals (HTTP 429); pushing a change to `docs/` only republishes the page. The chain keeps one of GitHub's machines occupied (mostly waiting) around the clock, which is free for a public repository. To pause updates, cancel the running run; to stop them, disable the workflow in the Actions tab. **Reading stores**: up to 12 stores are read at once (`workers`), each one page at a time with a second between requests, so no store is asked faster however many are read side by side. A store that answers 429 (too many requests) is left alone and come back to at the end of the run, then retried with waits for ten minutes at most. When most stores refuse at once it is the machine's address being turned away, so the run ends there and the next one tries again. The metrics page's **Updates** table logs every run: stores read, minutes, requests and refusals.
- The **`data` branch** holds the latest `state/` (tracking files), `catalog/` (each store's in-stock items that are not on the list), `data.json` (listings) and `metrics.json` as a single commit that each run replaces, so the repository doesn't grow with every update. A run that ends with under 80% of the products tracked before stops instead of saving. To build locally, copy `state/` and `catalog/` into `data/` and the two JSON files into `docs/` first.

On the page:

- **Tabs**: **Followed** shows items you star (☆); stars are saved in the browser, and a starred item stays there with its last known details after it stops being listed. **From my brands** shows everything else from the brands of your followed items, and from any brand you look up there: type a name in **Look up a brand** and pick it (✕ on its chip drops it again). **Everything** is the full listing. Filters include men's / women's / kids, and **In stock** (Followed tab only, since everything else listed is in stock).
- **Category** is a drop-down of tick boxes. Clothing is split into kinds (tops, bottoms, footwear…), and the arrow beside a kind opens its types (jeans, trousers, shorts…). Tick single types, a whole kind, "Clothing (all)", or leave everything unticked for any category. To find one brand's jeans at the best price: look the brand up under From my brands, tick Jeans, sort by Price.
- **My sizes** hides items not in stock in the sizes picked under "Settings". `build.py` converts each store's labels (LG, 50 (Large), Japanese 3, EU 43, 27.5 cm…) to letter sizes, waist inches and US men's shoe sizes; the tables are at the top of its "sizes" section.
- **Your own categories**: ⋯ on any card puts the item, or its store, into categories you name yourself ("shirts", "blue", "gift shops"…). The two "my categories" menus in the filter bar then filter by them. The same menu marks a store or brand "not interested", which hides it everywhere except the "Hidden: not interested" view.
- **High-volume stores**: the count line says how much of the list they make up, with a link to hide them (also a switch in "Settings"). It hides stores that list far more items than the rest. A store is flagged when its count of qualifying items (before the cap below) is above Q3 + 1.5 × (Q3 − Q1) of items-per-store, the box-plot rule for outliers. Stores you put in a category are never hidden.
- **Men's / women's** uses the labels stores put in titles, product types and tags; unlabelled items count as unisex.
- **Top picks** (the default sort) ranks by discount plus bonuses for followed brands, your size, a lowest-tracked price and new arrivals (weights in `score()` in `docs/index.html`). The discount counts half for its size and half for how unusual it is at its store.
- **Deal for its store / brand**: stores have habits (one marks everything 70% off, another rarely passes 20%), so these sorts rank a markdown by how it compares with the other markdowns at the same store, or of the same brand across all stores: its mid-rank percentile among them (discounts within 2 points count as ties, which count half), pulled toward 50% when there are few of them (`SHRINK`). Every discounted card shows the typical (median) markdown at its store and for its brand ("Typical: store 37% · brand 40%"); hover the discount badge for how this one compares.
- Every sort has a direction button beside it (high to low, newest first, A to Z, and back).
- **Tracking**: every product in a store's catalogue is recorded, on sale or not, in `data/state/<store>.json`: a point of time, price, the store's percent off and whether it is in stock, added each time one of them really changes (a price move under 3% is exchange-rate drift at stores that quote converted prices; products gone for 90 days are dropped). A product that leaves the catalogue is marked with when. Each product also keeps its brand, kind, the day the store published it and, while it is on sale, which sizes are in stock (stores don't publish stock counts; the sizes left are the nearest thing). So a **quiet price cut** shows up too: an item with no "was" price that is at least the minimum discount below the highest price tracked here is listed with a green **↓ tracked** badge. When a store moves many prices by the same percentage at once with its discounts unchanged (a repricing or a currency swing), the items are labelled "Store-wide price change" and left out of the Price change sort. **New** means the item joined the list in the last 3 days; what a store's first read finds gets no date.
- **Brand files**: the list holds sale items, but every other in-stock item is kept too, per store in `data/catalog/`, and regrouped by brand into `docs/brands/<n>.json` (512 files; a brand's number comes from its name, `brand_file()` in `build.py` and `bucket()` in the page). The page fetches only the files for the brands of your followed items, so **From my brands** shows a brand's whole range, full price included (pick a minimum discount to see only markdowns), and a followed item keeps its current price after its sale ends. `docs/brands/index.json` lists every brand with its item count, for the brand lookup. `py build.py --brands` regroups the catalogue without fetching anything.
- **Recent changes** (Followed tab): when fresh data replaces the saved copy of a followed item, the page notes what changed (price down or up by 3% or more, sold out, back in stock, your size gone or back, no longer in the shop) and keeps the notes for two weeks.
- **Deal facts on cards**, where tracking has seen enough: when the sale began, whether the "was" price was ever charged here before the sale (and for how long), and when an item came back into stock.
- **Sales starting and ending**: when a read finds many products newly marked down (at least 20, and 5% of the store's in-stock range), or many back at full price, the store's tracking file records a sale starting or ending. These events are kept for good, so a sale calendar builds up over the year. Sales run by discount code don't appear in store feeds.
- **Site metrics** (`docs/metrics.html`, linked at the foot of the page): per store and per discount band, how long deals stay available (a Kaplan-Meier estimate, so deals still running count for as long as they have been watched), how they end (sold out, sale ended, taken down), how often the price is cut again, how often a "was" price is higher than anything tracked before the sale, each store's share of products on sale and typical discount day by day, sales starting and ending, the share of all in-stock products on sale day by day, store-wide price changes and failed reads. Rates from fewer than 20 deals are not shown, and how deals end and how often they are cut again count only deals that began at least two weeks ago (younger ones would make sell-outs look too common and further cuts too rare).
- **Price history**: Cards show a small chart once an item has more than one price, with today's price as a dot: green at its lowest tracked price, red at its highest, yellow in between, and the **Price change** sort uses it: it lists only items whose price moved 3% or more while tracked, from the biggest drop below its tracked high to the biggest rise above its tracked low (the direction button flips it). The dot shows whether an item is still at its lowest or highest tracked price.
- Stars, categories, sizes and hidden stores and brands live in the browser; Settings → Backup downloads them as a file and loads one back on another device. Starred items keep a copy that is refreshed while they are listed, so after they drop out they still show their last known price. Hiding a store or brand from ⋯ takes effect at once, with Undo.
- **Ranked sorts** (Top picks, Deal for its store / brand) never show more than 2 items in a row from one store in the first 600, unless you pick a store; the other sorts keep strict order.
- **Layout**: on phones the tabs and search stay pinned and the other filters fold behind a Filters button. The count line shows how long ago the data was updated (amber after 6 hours: the hourly updates have probably stopped). Price-history dots: green ↓ at its lowest tracked price, grey in between, amber ↑ at its highest.
- **Ask the assistant** opens a chat with Claude that sees what you have on screen (and decides whether your question is about it), searches the site's items, knows your sizes, follows and categories, shows item cards in the conversation and remembers preferences you tell it. It needs your own Anthropic API key, pasted into the panel: the key is kept in that browser only (separate from the Backup box) and is sent only to Anthropic, so it is never part of the site or the repository and nobody else can use it. The Web switch lets it search the web and open links; the site's own items always come first.
- Prices in other currencies also show an approximate US dollar value, using rates fetched from open.er-api.com at build time.

Run locally:

    py build.py
    py -m http.server 8000 -d docs     # then open http://localhost:8000

Settings in `stores.json`: `min_discount` (percent off needed to be listed), `max_pages` (250 products per page, per store), `max_items_per_store` (optional cap, keeps each store's deepest discounts; unset means no cap), `workers` (stores fetched at the same time), `delay_seconds` (pause between requests to one store).
